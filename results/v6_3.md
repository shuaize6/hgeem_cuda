# v6.3：fragment 复用与输出暂存缩减（2026-11-05）

**结论：v6.3 是偏向大方阵的独立实验，不能整体替代 v6.2。4096³ 的三批 36 次配对均更快，合并中位时延 8.068505→7.084905 ms，吞吐提升约 13.9%、时延降低约 12.2%；达到默认 cuBLAS 的 72.7%。1024³ 时延反而增加约 13.4%，继续保留 v6.2。**

## 改动与映射

- 新增 `kernels/hgemm_v6_3.cu`，注册到原 CMake、头文件和 benchmark；v0～v6.2 kernel 与本轮开始快照逐字节相同。原有未提交的 v6.1/v6.2 工作保留。
- block tile 仍为 64×64×32，shared A/B 行跨度仍为 48/80 half，128-bit 搬运和非对齐/尾部标量补零规则保持不变，无 cp.async。
- 线程由 256→128，即 4 个 warp。warp 的行列位置为 `(warp/2)*32`、`(warp%2)*32`，每 warp 计算 32×32 输出；两个 A fragment 与两个 B fragment 做 2×2 组合。每个 k16 步，全 block fragment 加载从 24→16 次，乘加总量不变。
- 每线程循环搬两个 A/B 的 8-half 包，覆盖完整输入 tile。两次 block barrier 仍分别保护输入可见性和输入覆盖时机。
- 输出暂存由 `float[64][64]` 改为 `float[32][64]`。第 0 轮输出全 block 的行 0–15、32–47，第 1 轮输出 16–31、48–63；每轮先 collective store、block barrier、带边界检查写回，再 barrier 后复用暂存。所有线程参与 barrier。
- 输入占 11 KiB、输出暂存占 8 KiB，union 峰值降为 11 KiB。编译为 56 registers/thread、0 stack/0 spill；v6.2 为 56 registers/thread、16 KiB shared。

## 先验证假设，再调整

先扩展了 v6.2 与现有默认 cuBLAS 的八组尺寸对照，确认 v6.2 的 1024³ 优势不适用于大方阵和长方形。

第一次 v6.3 仅改变 fragment 复用，仍保留 16 KiB 输出暂存。正确性和 sanitizer 均通过，但多数对齐尺寸变慢。1024³ NCU 显示 LDSM 393,216→262,144，shared load 冲突约 158 万→105 万；寄存器 62，无 spill，但 shared 只允许 5 blocks/SM，实际 occupancy 从约 58% 降到约 36%。这一阶段的三批计时、源码及 NCU 均保留，不混入最终结果。

据此才将输出分两轮暂存。最终 shared 限制变为 8 blocks/SM（NCU 分配包含 driver 开销），寄存器降到 56。4096³ 的实际 occupancy 回到约 65%，出现稳定的配对收益；1024³ 仍不足以抵消额外指令和输出阶段开销。

## 正确性与数值口径

- 最终 v6.3 小尺寸 21 组 × 3 种输入 × 2 种输入基址偏移（0/1 half）=126 项 CPU double 全输出检查通过。
- 1024³、1023×1025×1007，各 3 种输入，另 6 项完整 CPU double 检查通过，总计 132 项。
- 包含 K=1/2/8/14/15/16/17/18/24/32/33/34/40/48/50/66、tile 边界、奇数行跨度、非对齐地址。dyadic 和交替符号输入要求最终 half 精确一致；连续随机输入沿用 gamma_K 加 FP16 输出舍入误差界，未放宽。
- 最终 memcheck、racecheck、synccheck 全部 0 errors；racecheck 0 warnings。原始 1024³ 总表所有版本通过 cuBLAS 容差检查。
- 八组性能尺寸在每批计时前，用同一 dyadic 输入做全输出 cuBLAS 对照；所有不一致位置逐个计算 CPU double，另独立抽样 256 个位置。三批均通过自写 kernel 的 CPU 检查。2048³/4096³ 没有做完整 CPU 全矩阵参考，不将抽样称为穷尽验证。
- 初始 harness 把 cuBLAS 逐位相同当作要求，在 512×2048×1024 中报告 768 个差异，误中止了计时。逐个 CPU 核对后，v6.2/v6.3 在这些位置均正确；奇数大矩阵也有 45 个差异。保留默认 cuBLAS 配置，改为 CPU 独立裁决，未通过放宽自写 kernel 的 dyadic 检查来消除错误。这里只确认数值差异，未定位 cuBLAS 内部具体舍入阶段。失败及诊断日志在原始文本记录中保留。
- 未覆盖非有限输入、零/负尺寸、超大索引；未搜索其他 cuBLAS 算法或 cuBLASLt。

## 独立计时

RTX 3060 Laptop 6 GB / sm_86、WSL Ubuntu 24.04、driver 591.74、CUDA 12.8.61、g++ 13.3、CMake 3.28.3、Nsight Compute/Compute Sanitizer 2025.1；CMake 目标仍为 sm_86，-O3 -lineinfo，无 fast-math。

FP16 输入/输出、FP32 累加，默认 `CUBLAS_COMPUTE_32F` / `CUBLAS_GEMM_DEFAULT` / `CUBLAS_DEFAULT_MATH`。同一输入输出地址和 nonblocking stream，H2D 也在该 stream 上。CUDA events 仅计设备计算，排除分配、复制、初始化和正确性检查。重复访问同一输入，属于缓存复用场景。

3 个独立进程，每尺寸 12 轮，3 个版本循环轮换执行顺序。每尺寸开始交替预热 `10*repeat*3` launches；每次计时前另预热 10 次。repeat 为 200（512³、1024³、两组长方形、短 K、奇数尺寸）、25（2048³）、10（4096³）。全部计时结束后才做 NCU。

每个尺寸/版本单次 launch，采集 LaunchStats、Occupancy、SpeedOfLight、SchedulerStats、WarpStateStats、MemoryWorkloadAnalysis_Tables、SourceCounters，以及 Tensor/总指令计数。使用默认 NCU 缓存/时钟控制、无应用计时预热；Profile 时延不用于上面的性能结论。

| Tensor pipe active (elapsed) % | 31.26 | 30.27 | 37.83 | 41.77 |

LDSM 和 shared read 冲突约减少三分之一，与 fragment 复用假设一致。两版本 Tensor 指令数、global load 指令数相同，均没有 spill。最终 SASS 可见 LDG.E.128、STS.128、LDSM 和 HMMA。

总动态指令数反而增加，所以不能只看 LDSM 或冲突计数。4096³ 时两个版本 occupancy 接近，v6.3 Tensor pipe 利用率提高，配对计时也改善；1024³ 时 v6.3 实际 occupancy 仍更低，理论 waves/SM 由 2.13→1.07，有尾波影响的可能，但未单独量化其成本。输出分段和线程映射也改变了指令开销，不能把收益全部归于某一个计数。

cuBLAS 在 1024³ 使用 `ampere_fp16_s16816gemm_fp16_256x128_ldg8_f2f_stages_32x3_nn`；4096³ 使用 `Kernel2<cutlass_80_tensorop_f16_s16816gemm_relu_f16_256x128_32x3_nn_align8>`，动态 Tensor 指令与自写 kernel 相同。4096³ cuBLAS 总动态指令约 71,258,112，明显少于 v6.3 的 473,859,932。下一步可针对大矩阵研究更大的 block tile 与数据复用，以减少搬运及控制指令；小矩阵继续保留 v6.2。

初次按 kernel 名 `.*gemm.*` 过滤漏掉了 cuBLAS 4096³ 的 `Kernel2`；最终已去除过滤重采并确认报告包含测量值。原工具日志保留。
