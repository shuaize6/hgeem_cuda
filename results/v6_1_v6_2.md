# v6.1 / v6.2 实验（2026-11-01）

**结论：padding 和向量化均获得稳定收益。当前 RTX 3060 Laptop、1024³、cuBLAS 默认算法下，v6.2 达到约 113.6% cuBLAS；不能推广为全面超过 cuBLAS。**

## 两步改动

1. `kernels/hgemm_v6_1.cu`：从 v6 独立复制。A shared 行跨度由 32→48 half，B 由 64→80 half，WMMA leading dimension 同步修改。64×64×32 tile、warp 映射、计算与 barrier 保持不变。A/B 共 11 KiB，仍小于 union 的 16 KiB 输出区。
2. `kernels/hgemm_v6_2.cu`：基于 v6.1，每线程每个 K tile 各搬运一个 A/B 16-byte 包（8 half）。A 每行 4 个包，warp 覆盖 8 行；B 每行 8 个包，warp 覆盖 4 行。完整且 16-byte 对齐的源地址走 uint4 加载；尾部或未对齐地址逐元素加载/补零，再存入对齐 shared 包。没有引入 cp.async，也没有改 WMMA 或同步。

两个版本加入原 CMake、头文件及 benchmark；原表格继续显示 `% cuBLAS`。v0～v6 原 kernel 未改变，旧 benchmark 模式保留，新模式单独进行各阶段对照。

## 发现并修复测试程序的复制顺序问题

最初 v6.2 小尺寸通过，但无 sanitizer 的大尺寸随机输入出现错误；racecheck 下反而通过。扩展 Matrix 测试工具此前使用默认 stream 的 pageable `cudaMemcpy`，随后在 nonblocking stream 启动 kernel，缺少明确依赖。按 [CUDA Runtime 同步语义](https://docs.nvidia.com/cuda/cuda-runtime-api/api-sync-behavior.html)，这类 H2D 调用返回时 DMA 可能尚未完成。

已将两次输入复制改为同一 nonblocking stream 上的 `cudaMemcpyAsync`，用 stream 顺序建立 H2D→kernel 依赖。此次没有为修复错误而修改 v6.2 kernel。修复后三次独立的大矩阵完整验证全部通过，并重测 v6/v6.1 基线。现象与该顺序漏洞一致；不能把 sanitizer 下未报错视为不存在跨 stream 问题的证明。

下列主表全部来自修复后的同一可执行文件。修复前 v6.1 阶段测量和 v6.2 失败日志保留在归档中，作为实验过程记录，不混入最终结果。原普通 benchmark 的复制和 kernel 都在默认 stream，不属于这个扩展工具问题。

## 正确性与资源

- v6.1：18 组小尺寸 + 1024³、1023×1025×1007，各 3 种输入，共 60 项 PASS；修复测试工具后完整复测 PASS。
- v6.2：原 18 组小尺寸加 65×72×40、63×64×8、65×72×24，各 3 种输入，分别测试基址偏移 0/1 个 half，共 126 项；两组大尺寸各 3 种输入，共 132 个不同测试项全部 PASS。大尺寸额外连续复测三次，无失败。
- 输入包括随机 dyadic、连续均匀随机、交替符号。逐元素使用实际 half 输入的 CPU double 参考；精确可累加输入要求 half 结果相等，其他使用原 gamma_K 累加及 FP16 舍入误差界，未放宽。输出 NaN 预填检测漏写。
- 两版本均在最终复制顺序下运行 memcheck、racecheck、synccheck：0 errors；racecheck 0 warnings。原 1024³ cuBLAS 对照表也 PASS。
- 未覆盖非有限输入、零/负尺寸、超大索引溢出；性能只测试 1024³，不能代表奇数尺寸/标量回退路径的速度。

## 无 NCU 计时（最终同批结果）

1024³、FP16 输入/输出、FP32 累加。cuBLAS 使用同一输入、输出地址、stream，沿用 CUBLAS_COMPUTE_32F 与默认 math/algorithm。3 个独立进程，每批交替预热 4000 launches，12 轮，每项预热 20 次、CUDA events 计时 200 次。每轮循环轮换四个版本的位置。重复访问固定输入，属于缓存复用场景；不含分配、H2D 与 cuBLAS 初始化。全部计时完成后才运行 NCU。

## Profile 解释

单次 1024³ launch，约 33 replay passes，默认 NCU 缓存/时钟控制，无应用预热。采集 LaunchStats、Occupancy、SpeedOfLight、SchedulerStats、MemoryWorkloadAnalysis_Tables、SourceCounters 和 Tensor/总指令计数。NCU 时延不用于 benchmark 结论。

| 指标 | v6 | v6.1 | v6.2 |
|---|---:|---:|---:|
| Shared load bank conflicts | 6,815,744 | 1,572,864 | 1,578,254 |
| Shared load wavefronts | 8,453,168 | 3,203,903 | 3,186,855 |
| Shared excessive wavefronts（读写合计） | 6,914,048 | 1,671,168 | 1,933,312 |
| Global load 指令数 | 1,048,576 | 1,048,576 | 131,072 |
| Shared store 指令数 | 1,064,960 | 1,064,960 | 147,456 |
| 总动态指令数 | 31,156,224 | 31,223,808 | 5,308,416 |
| Tensor 指令数 | 524,288 | 524,288 | 524,288 |
| Tensor pipe active（elapsed %） | 11.49% | 14.72% | 30.93% |
| Achieved occupancy | 46.17% | 45.92% | 58.45% |

v6.1 的主要证据是 shared read 冲突/wavefronts 显著减少，资源占用和搬运指令数保持相近，独立时延随之下降。仍有冲突，并非完全消除。
v6.2 保留该布局，SASS 出现 LDG.E.128 / STS.128。1024³ 对齐路径的 global load 指令恰好减少到 1/8；这不是总传输字节减少到 1/8。总动态指令约减少 83%，寄存器也下降，Tensor pipe 利用率提高。
v6.2 的 shared excessive wavefronts 合计反而比 v6.1 增加，但独立时间仍大幅下降，说明不能把单个冲突/波前计数当作端到端成本。也不能把寄存器减少与指令减少的贡献分别量化为独立加速倍数。

cuBLAS 仍选择 `ampere_fp16_s16816gemm_fp16_256x128_ldg8_f2f_stages_32x3_nn`。这里胜过的是该尺寸下的默认选择，并未搜索 cuBLASLt 或其他 cuBLAS 算法。下一步宜先扩展尺寸与算法基线，再决定是否继续处理剩余 shared load 冲突或增加流水线。
