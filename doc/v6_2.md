# v6.2：128-bit 搬运与安全边界路径

[上一版 v6.1](v6_1.md) · [学习目录](README.md) · [下一版 v6.3](v6_3.md)

对应当前源码：[kernel](../kernels/hgemm_v6_2.cu#L37)、[launcher](../kernels/hgemm_v6_2.cu#L113)。测量与测试证据见 [结果分析](../results/v6_1_v6_2.md)。本页解释实现，2026-11-05 核对源码，未重新测量性能。

## 一次搬 8 个 half

保留 v6.1 的 64×64×32 tile、AS=48、BS=80 和 WMMA 映射。新增 `load8`，使用 16-byte `uint4` 搬运一个包含 8 个 half 的包。uint4 只承载原始位模式，不把 half 数值转换为整数。

## 256 个线程恰好覆盖 tile

A、B 各有 2048 个 half，即各 256 个包。每个线程各搬一个 A 包和一个 B 包：

| 对象 | 行 | 包首列 | 一个 warp 覆盖 |
|---|---|---|---|
| A | `tid/4` | `(tid%4)*8` | 8 行 |
| B | `tid/8` | `(tid%8)*8` | 4 行 |

这是搬运映射；计算仍由 8 个 warp 各完成 32×16 输出。

## load8 的三个检查

1. `firstValid` 确认包的首元素在有效行列内；否则 src 使用合法 base，避免先构造越界指针。
2. `col+7<cols` 确认八个元素完整合法。
3. `(uintptr_t(src)&15)==0` 确认实际地址 16-byte 对齐，不能仅根据矩阵维度猜测。

完整且对齐时读一个 uint4；否则将 uint4 的存储区视作八个 half，逐元素读取或补零，最后统一写入 shared。shared 行跨度与包首列共同保证目标 16-byte 对齐。

奇数 N/K、尾包或输入基址偏移一个 half 时，仍是本 kernel 的安全标量路径，不回退旧版本。

## 同步与实际收益

load8 仍是普通同步加载/存储，没有引入 cp.async。所有线程搬完后执行 block barrier，随后 WMMA 消费数据，计算后再 barrier。

在 1024³ 的对齐路径上，global load 指令由 1,048,576 降到 131,072，即 1/8；总输入字节没有因此变成 1/8。寄存器也从 70 降到 56，是编译后的观测结果。

本阶段还修复了 benchmark 的 H2D stream 顺序：输入复制与 kernel 现在使用同一 nonblocking stream。学习时要区分测试工具的依赖漏洞和 kernel 的边界处理。

## 阅读与验证

先从 launcher 确认 block/grid，再沿 kernel 的加载、同步、计算、输出顺序阅读。可运行以下现有入口：

```bash
./build/bench_hgemm --test-v6-2
```

该命令的实际覆盖范围以 [测试索引](../results/README.md) 为准；测试命令示例不代表本次文档整理重新执行过验证。
