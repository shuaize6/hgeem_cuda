# v3：4×4 寄存器分块与 padding

[上一版 v2](v2.md) · [学习目录](README.md) · [下一版 v4](v4.md)

对应当前源码：[kernel](../kernels/hgemm_v3.cu#L14)、[launcher](../kernels/hgemm_v3.cu#L100)。测量与测试证据见 [结果分析](../results/v3.md)。本页解释实现，2026-11-05 核对源码，未重新测量性能。

## 当前构建使用哪个 v3

当前 `kernels/hgemm_v3.cu` 的 B 是 `Bs[BK][BN+16]`，已经带 padding。`kernels/variants/hgemm_v3_original.cu` 保留无 padding 版本，另有 padded 变体；根 CMake 只编译主文件。阅读早期 v3 Profile 时必须区分这两种布局。

## 4×4 输出映射

BM=BN=64、BK=16、TX=TY=16。256 个线程各维护 `float acc[4][4]`，输出映射为：

\[
C[64b_y+t_y+16i,\;64b_x+t_x+16j],\qquad i,j=0,1,2,3.
\]

例如线程 `(3,2)` 负责行 `{2,18,34,50}` 与列 `{3,19,35,51}` 的全部 16 个交点，不能把它理解成连续 4×4 方块。

## K 步内的复用

各线程先合作搬四个 A、四个 B。每个 k，从 shared 读四个 a 和四个 b，双重循环执行 16 次乘加：

```cpp
for (int i = 0; i < 4; ++i)
    for (int j = 0; j < 4; ++j)
        acc[i][j] += a[i] * b[j];
```

8 次源级 shared 读取支持 16 次乘加，平均降为 0.5。两处 barrier、无效输入补零、输出逐元素掩码与 v2 同理。

## padding 到底改变了什么

B 的逻辑宽度还是 64，实际一行占 80 个 half。索引仍写 `Bs[k][tx+j*16]`，C++ 数组类型自动按 80 个 half 计算跨行地址。shared 总量从 4096 增到 4608 bytes；global B 的行跨度 N 和输出坐标不变。

历史 Profile 显示这种 padding 消除了所测 B shared store 冲突；这不意味着所有指令或任意布局的冲突都会消失，也不等于端到端同比例加速。结果页区分无 padding/有 padding 的指标。

## v4 将改什么

v3 仍逐个 half 搬运。v4 用 half2 减少 global→shared 搬运指令，同时保留这套相隔 16 的输出映射。注意 v4 的 B shared 恢复为未 padding 的 64 列。

## 阅读与验证

先从 launcher 确认 block/grid，再沿 kernel 的加载、同步、计算、输出顺序阅读。可运行以下现有入口：

```bash
./build/bench_hgemm 31 33 17
```

该命令的实际覆盖范围以 [测试索引](../results/README.md) 为准；测试命令示例不代表本次文档整理重新执行过验证。
