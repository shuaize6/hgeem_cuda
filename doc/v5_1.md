# v5.1：cp.async 双缓冲

## 两套 buffer 和三个阶段

shared 改为 `As[2][64][16]`、`Bs[2][16][64]`，共 8 KiB。计算仍是 256 threads 各算相隔 16 的 4×4 输出。`load_tile_async` 只发出拷贝，提交和等待由调用者控制。

1. **预加载**：把 tile 0 发到 buffer 0，提交一个组。
2. **主循环**：`current=tile&1`，`next=current^1`；有下一 tile 就先向另一 buffer 发起拷贝并提交，然后等待当前 tile。
3. **收尾**：没有下一 tile 时改用 `wait_group 0`，消费最后一个 tile 后输出。

## 三个 tile 的例子

| 当前计算 | 新预取 | 等待方式 | 本轮结束后可复用 |
|---|---|---|---|
| tile 0 / buffer 0 | tile 1 / buffer 1 | wait_group 1 | buffer 0 |
| tile 1 / buffer 1 | tile 2 / buffer 0 | wait_group 1 | buffer 1 |
| tile 2 / buffer 0 | 无 | wait_group 0 | 两者 |

`wait_group 1` 允许最近的一个组尚未完成，在这里就是下一 tile；它保证更早的当前 tile 组完成。只有一个 tile 时，直接走最后一行的等待方式。

## 两个 barrier 的职责

等待指令是 per-thread。等待后的第一个 `__syncthreads()` 汇合全部生产线程，当前 tile 才能跨线程消费。计算后的第二个 barrier 保证所有消费者读完，下一次循环才允许把 tile t+2 写到 tile t 曾使用的 buffer。

`hasNext`、tile 数量和 current/next 在 block 内一致，不让部分线程跳过 barrier。异步指令允许重叠，但实际收益取决于计算是否足以隐藏搬运、资源占用以及编译安排。

## launcher 的回退

K 或 N 为奇数时，`launch_hgemm_v5_1` 直接调用 v5；这些测试覆盖 launcher 的安全回退，不是对双缓冲 kernel 的原生路径验证。偶数短 K、两 tile、尾 tile 的测试才直接覆盖流水线时序。

历史编译占 65 registers/thread，分配粒度导致驻留上限下降。下一版只改变编译资源约束，保留本页所有映射与同步逻辑。

## 阅读与验证

先从 launcher 确认 block/grid，再沿 kernel 的加载、同步、计算、输出顺序阅读。可运行以下现有入口：

```bash
./build/bench_hgemm --test
```

该命令的实际覆盖范围以 [测试索引](../results/README.md) 为准；测试命令示例不代表本次文档整理重新执行过验证。
